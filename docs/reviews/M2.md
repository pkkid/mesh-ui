## 1. Questions

1. **Real-network checks by agents cannot reach your session.** You allowed
   gentle read-only calls for this run, but `pnpm mesh-ui` always runs with a
   scratch user data dir, so every attempt (M2.4-fix, M2.9) got
   `not_signed_in` and sent nothing to eero. The shape checks below stay
   manual. Options: (a) keep it this way and run the Manual checks yourself
   (recommended: matches AGENTS.md's "never read the maintainer's session"
   rule); (b) add a documented opt-in, for example
   `MESH_UI_USER_DATA_DIR=<real dir>` for one command when you ask, written
   into AGENTS.md's Testing exception. Nothing waits on it.
2. **eero detail Uplink card is a compact row, not the topology map.** In
   the hero, the map from the eeros page clipped labels and its chips covered
   short links (#72). It reuses the same link look, chips and colours.
   Options: (a) keep the row (recommended); (b) fit the map into the hero in
   a fix task. Look: [gateway](https://github.com/pkkid/mesh-ui/blob/assets/M2.9-screenshots/demo-gateway-dark.png?raw=true),
   [Office](https://github.com/pkkid/mesh-ui/blob/assets/M2.9-screenshots/demo-office-light.png?raw=true).
3. **Radio utilisation meters are neutral, not the band colour** in mockups
   03 and 04 (#67, #72), following the restrained-colour rule (colour only
   for chart series and status). Options: (a) keep neutral (recommended);
   (b) use the band series colour from `chartColors.ts`.
4. **Mesh bars: 0 to 5 in data, 4 drawn.** eero reports 0 to 5 bars; the
   icon draws 4 and the text says "2 of 5 bars". Excellent is 4 to 5, Good
   3, Weak 2, Poor 0 to 1 (M2.1). Options: (a) keep (recommended); (b) draw
   5 bars.

## 5. Decisions made

Each can be reversed by number.

1. Summary counts are `{key, count}` lists, largest first, with a null row
   for none, Unassigned or unknown maker (#62).
2. Hop, mesh quality, health issues and the internet verdict are computed in
   core; backends cannot fill them (#62, #67).
3. The verdict uses only the last speed test; with no test or plan it reads
   "... is up" (#66).
4. Plan speeds use the shared Mbps formatter: "1,200 Mbps", not "1.2 Gbps"
   (#66).
5. The demo plan lives in `DEMO_SETTINGS` applied by the demo hosts;
   `fileSettings` takes optional defaults, and an existing file wins (#70).
6. Firmware history fetches 50 rows, sorts newest first, then trims to
   `limit`; a 404 or 405 returns `[]` (#64).
7. `eero.list` and `eero.get` also read the network object for subnet and
   gateway IP (#64). Auto channel stays null: no known eero field.
8. `network.health` reads eeros and devices only when something is wrong; a
   healthy poll is one request (#67).
9. The eero client shares identical session GETs while in flight and for 5 s
   after success; writes, sign-in and sign-out clear it; failures are never
   shared (#74).
10. Reservations stay in the static range (.4.2 to .4.99); ordinary demo
    devices moved into the pool (#71).
11. The palette runs only query commands; lucide icons load in a separate
    chunk on first open; zod runs `jitless` because of the CSP (#65).
12. One device icon map (Devices' choices plus Overview's camera) (#60).
13. Mockup legend reads "Good (3 to 5 bars)" and the eeros page doc was
    corrected to match (#63, #67).

## 6. Numbers, surprises, open items, next

**Numbers.** 15 PRs, 331 to 442 tests, `pnpm check` 3.8 s. Up to 6 workers
at once; no worker needed a resume.

**Surprises.**
- The eero client burned its whole 80 a minute budget in about 1 s on
  Overview plus one eero page, because each area re-read the network,
  permissions and account. Later reads then waited up to a minute. It
  showed only in a multi-shot `--fake` run, and the same path runs against
  the real API. Fixed in #74 with a page-load request test.
- Lead review caught copied logic in five places (clipboard, live-rates hook
  three times, MCP naming, `needsConfirm`). All are now single
  implementations, except `MeshBars` in `EerosList.tsx` (carried to M3).
- The demo had no internet plan, so the first Internet shots never showed
  the mockup's plan meters (#70).
- Two macOS CI flakes (EPIPE in the CLI tests, a CPU-starved fixture test),
  both explained and fixed in #73.
- The parallel run hit GitHub's API rate limit once near the end.

**Open items (carried in the roadmap).** Section header wraps with a long
subtitle; `MeshBars` copy in Overview; mockups 05, 10 and 14 use old
`3c:22:fb` MACs; `AreaChart` has no fixed `max` (plan-scale speed chart);
no host save dialog for CSV; palette dimming by capability or bridge mode
and the "no permission" state; `autoChannel` source.

**Process lessons** (proposed edits to the milestone skills):
- Worker prompt: "Before writing a helper, search for one; if a sibling
  story owns it, report needs-file instead of copying."
- `milestone-plan`: for every page story, check the demo fixtures cover each
  state the mockup shows (plan set, leased devices, blocked, guest) and add
  them to the core story.
- Real-network permission: say in the prompt how a CLI reaches a session, or
  that it cannot (question 1).
- Lead: batch `gh` calls; avoid per-PR loops near the API limit.
